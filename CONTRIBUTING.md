# Contributing to Uatu

Thank you for helping. Uatu is licensed under the [Apache License 2.0](LICENSE)
and accepts contributions through GitHub pull requests under the same license.
Improvements to documentation are as welcome as code. If you are new, start with
documentation or a small bug fix.

## Project structure

- [project-uatu/backend](https://github.com/project-uatu/backend): this
  repository, the collector and API.
- The frontend and the Helm chart live in separate repositories and are not
  accepted here.

## Acceptance policy

A pull request is more likely to be accepted when it:

- Addresses an open issue. If none exists, open one to discuss the problem and
  the proposed solution first.
- Keeps backward compatibility for the API, configuration and database
  migrations, including rolling updates between releases.
- Follows the conventions of the surrounding code, has good test coverage and
  is documented. Exported names and non-trivial declarations have doc comments.
- Passes the [validation](#validation) checks.

A maintainer's endorsement is enough to merge. Substantial changes may need more
reviewers, or be split into several pull requests.

## AI coding assistants

Using an AI assistant is fine, but you are responsible for understanding and
reviewing everything you submit.

- Point your assistant to [`AGENTS.md`](AGENTS.md) and ask it to follow the
  guidelines there, including the instruction files it references.
- Disclose the assistance in the pull request description and in each commit
  with an `Assisted-by: <agent>/<model>` trailer.
- Assistants must not add `Signed-off-by` or `Co-authored-by` trailers. Only
  humans can certify the DCO, so the human author signs off.
- Keep PR descriptions, commit messages and code comments concise.
- Write your own replies to maintainers; we want to talk to you, not to your
  assistant.

## Developer Certificate of Origin

Every commit must be signed off to certify the
[Developer Certificate of Origin](https://developercertificate.org/):

```sh
git commit -s
```

The sign-off must use your real name, so no pseudonyms or anonymous
contributions. With `user.name` and `user.email` set in your Git config,
`git commit -s` adds it for you. Commits should also be cryptographically signed
(`git commit -s -S`).

## Commit messages and pull requests

- Follow [Conventional Commits](https://www.conventionalcommits.org/) strictly.
- Use lower case only in the subject, for example `fix: retry expired leases`.
- Do not put issue numbers in commit subjects or pull request titles; link
  issues in the description instead.
- `CHANGELOG.md` is generated by release-please. Do not edit it.

## Scope and architecture

- This repository is backend-only. The frontend lives in a separate repository.
- Keep Uatu lightweight: one static binary, a distroless non-root image and
  PostgreSQL through pure-Go `pgx`. Do not add Redis or message queues.
- Canonical state belongs in PostgreSQL. Replicas are stateless, and failed
  fetches must never overwrite stored data.
- Keep the executable in `cmd/uatu/` and application packages in `internal/`.
  Do not add packages under `pkg/`.
- Before a major change, such as schema or identity rules, collection contracts,
  API behavior, deployment topology or new sources, write an ADR under
  [`docs/adr/`](docs/adr/README.md) and obtain maintainer acceptance before
  implementing. Keep ADR changes separate from code changes.

## Code

- Follow [`.github/instructions/go.instructions.md`](.github/instructions/go.instructions.md).
- Start new Go files with `// SPDX-License-Identifier: Apache-2.0`.
- Update `README.md` when behavior, configuration, endpoints or commands change.
- Never commit secrets or tokens.

## Validation

Run these before opening or updating a pull request. CI runs the same checks:

```sh
gofmt -l .
go vet ./...
golangci-lint run
go test ./...
go test -race ./...
```

Unit tests must not use the network or a real `GITHUB_TOKEN`. Store integration
tests run when `UATU_TEST_DATABASE_URL` points to an isolated PostgreSQL
database; never use a development or production database. See
[Development](README.md#development) for setup.

## Reviews

Resolve review conversations as you address them, and keep pull requests green
before requesting another review.
